# 案例库

用这些案例来校准什么叫“必要改动”。

## 黄金案例：Web 启动被原生模块导入阻断

目标：
- 让 Web 本地先启动起来。

观察到的阻断链：
- 一个 Web 路由导入了弹窗组件。
- 弹窗组件导入了局域网分享工具。
- 这个工具在模块顶层导入了原生专用 static server。
- 用户甚至还没点“分享”，Web 就在模块求值阶段直接崩了。

有效做法：
- 修复只落在失败导入链上。
- 让原生模块只在非 Web 平台才加载。
- 在现有 UI 文件里内联一个小的 `Platform.OS !== 'web'` 判断，收掉分享入口。

为什么这是好修复：
- 它直接移除了阻断点。
- 它没有引入依赖变化。
- 它没有改命令、改约定、改结构。
- 它把补丁严格绑在失败路径上。

## 失败案例：用户只要先解除阻断，却把范围扩成测试和 helper

错误扩张：
- 加 Jest。
- 加测试文件。
- 为了一个平台判断单独抽共享 helper。
- 再加一层 web-proxy helper。

为什么这是坏修复：
- 这些改动都不是“先启动起来”所必需的。
- 它们扩大了 review 面积，也引入了新的决策点。
- 它们把任务从“解除本地阻断”改成了“顺手提升工程质量”。

规则：
- 如果用户的目标是先解除阻断，就不要用基础设施建设去扩大任务范围。

## 失败案例：未经要求去统一脚本和文档

错误扩张：
- 把现有代理脚本命令改成别的路径。
- 顺手改 README 文案去匹配新路径。
- 再加 wrapper 文件让这套新选择看起来更统一。

为什么这是坏修复：
- 它改动了并非阻断点的项目约定。
- 它在 ownership 和意图上制造了额外 review 噪音。
- 它把“修 bug”变成了“纠正项目”。

规则：
- 除非用户明确要求，或者当前路径根本无法满足目标，否则保留现有命令、脚本名和文档口径。

## 黄金案例：运行前置条件缺失，不是代码 bug

目标：
- 在 Web 本地看到远端内容。

观察到的问题：
- API 请求失败，因为本地代理服务根本没跑。

有效回应：
- 直接说清楚缺了什么前置条件，以及该执行什么命令。
- 不要补 fallback UI，不要加重试编排，不要在下层吞错，除非用户明确要求。

为什么这是好做法：
- 这个问题是环境问题，不是架构问题。
- 最短路径就是把前置条件说清楚。

## 工作总结

优先：
- 直接追阻断链
- 在现有文件里原地修复
- 保留现有命令和项目约定
- 明确报告运行前置条件

避免：
- 额外文件
- 为一次性条件抽 helper
- 文档抖动
- 依赖抖动
- 掩盖真实失败的 fallback
